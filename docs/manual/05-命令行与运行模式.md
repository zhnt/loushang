# 第4章 命令行与运行模式

> 文档版本：V1.0.0

说明 text、print、json、rpc、channel 和 TUI 等运行入口及其选择原则。

本章以用户可执行操作为主，命令和路径均应在目标安装环境中再次核对。

## 4.1 命令行结构

Loushang 主命令由全局参数、资源选择、会话控制、工具控制和消息内容共同组成。

### 功能要点
- 位置参数 messages 可承载直接消息，--prompt 用于显式提示。
- 列表和导出命令通常在完成操作后退出，不启动普通模型会话。
- 扩展可以在启动解析阶段注册附加参数。

### 操作步骤
1. 先确定本次是查询、一次性执行还是交互会话。
2. 再指定工作目录、模型、会话和工具。
3. 最后提供提示、命令或导出目标。
4. 通过退出状态和结果格式判断执行结果。

### 命令或配置示例
```text
loushang [options] [messages ...]
loushang --help
```

### 验证方法
- 参数组合没有互斥冲突。
- 运行模式、输出格式和会话策略符合调用方预期。

### 注意事项
- 自动化脚本应固定输出格式，不要解析面向人的可变文本。
- 扩展参数应以扩展自己的说明为准。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“命令行结构”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 4.2 Text 模式

text 模式面向终端中的普通交互与文本展示，是未显式选择其他模式时的重要入口。

### 功能要点
- 输出以人类阅读为主，可以包含流式文本和工具事件。
- 是否进入全屏 TUI 由 --tui、--no-tui 与终端环境共同决定。
- 持久化会话可用于后续继续、分叉和导出。

### 操作步骤
1. 确认 stdout 面向用户终端。
2. 选择模型和思考强度。
3. 按需启用工具事件渲染。
4. 完成后检查会话和诊断。

### 命令或配置示例
```text
loushang --mode text -p "分析当前任务。"
loushang --render-tool-events -p "执行并说明工具步骤。"
```

### 验证方法
- 文本输出完整并且终端编码正确。
- 工具事件不会被误当作最终回答。

### 注意事项
- 不要在依赖严格 JSON 的管道中使用 text。
- 大量输出重定向到文件时应关注终端控制字符。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“Text 模式”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 4.3 Print 模式

print 模式适合一次性提示和脚本调用，以简洁文本返回最终结果。

### 功能要点
- 该模式强调最终文本，不依赖全屏交互界面。
- 可以与明确模型、工具和工作日志配置组合。
- 调用方仍应检查标准错误和退出状态。

### 操作步骤
1. 使用 --mode print 指定模式。
2. 通过 -p 提供完整任务。
3. 将标准输出保存或传给后续程序。
4. 对写入任务检查实际文件差异。

### 命令或配置示例
```text
loushang --mode print -p "输出仓库摘要。"
loushang --mode print --no-tools -p "解释给定上下文。"
```

### 验证方法
- stdout 主要包含预期的最终文本。
- 失败时调用方能从状态码和 stderr 识别问题。

### 注意事项
- 不要假设自然语言输出具有稳定字段顺序。
- 机器集成优先考虑 json、rpc 或 channel。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“Print 模式”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 4.4 JSON 模式

json 模式用于需要结构化结果的脚本、测试和集成流程。

### 功能要点
- 机器可读输出应由 JSON 解析器处理。
- 列表、命令和导出操作还可能有各自的格式参数。
- 结构字段应按登记版本固定，升级时需要兼容性检查。

### 操作步骤
1. 显式指定 --mode json。
2. 避免把调试文本混入标准输出。
3. 用 JSON 解析器读取结果。
4. 对缺失字段、错误对象和非零状态建立处理分支。

### 命令或配置示例
```text
loushang --mode json -p "生成结构化执行结果。"
loushang --list-sessions --list-sessions-format json
```

### 验证方法
- 输出是合法 JSON，并包含调用方需要的核心字段。
- 错误路径不会被当作成功结果继续处理。

### 注意事项
- 不要依赖字段在文本中的排列顺序。
- 记录日志时应过滤可能包含敏感内容的消息字段。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“JSON 模式”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 4.5 RPC 模式

rpc 模式为外部宿主提供请求响应式会话控制，适合编辑器、测试探针和上层应用集成。

### 功能要点
- RPC 调用方负责保持协议读写边界和消息顺序。
- Method 与 Work Log 在当前产品边界下不支持 RPC 组合。
- 扩展命令与会话命令可通过运行时查询面发现。

### 操作步骤
1. 启动 --mode rpc 进程。
2. 按协议发送初始化和请求消息。
3. 处理流式事件、工具事件和最终响应。
4. 在进程结束前执行清理和会话保存。

### 命令或配置示例
```text
loushang --mode rpc
python examples/coding/13_rpc_mode_probe.py
```

### 验证方法
- 调用方能区分事件、响应和错误。
- 进程退出后没有残留半写入会话记录。

### 注意事项
- 不要把普通终端文本写入 RPC 标准输出通道。
- 协议消费者应设置超时、取消和异常恢复。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“RPC 模式”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 4.6 Channel 模式

channel 模式用于边界协议集成，强调稳定的消息通道和宿主控制。

### 功能要点
- 宿主需要明确输入、输出、取消和结束语义。
- 通道事件应与人类界面渲染解耦。
- 工具批准和外部副作用仍由宿主策略控制。

### 操作步骤
1. 确定宿主支持的 channel 协议版本。
2. 启动进程并建立输入输出通道。
3. 发送消息并消费事件。
4. 在取消或错误后等待明确的终止状态。

### 命令或配置示例
```text
loushang --mode channel
loushang --no-tui --mode channel
```

### 验证方法
- 消息不会跨请求串线。
- 取消后不会继续执行未经授权的工具动作。

### 注意事项
- Channel 面向集成开发者，普通终端用户应优先使用 text 或 TUI。
- 宿主必须保存足够日志以定位协议错误。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“Channel 模式”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 4.7 思考强度与输出

thinking 参数向支持该能力的模型表达推理强度偏好，可在速度、成本和复杂度之间进行选择。

### 功能要点
- 可选值包括 off、minimal、low、medium、high 和 xhigh。
- 提供方或模型可能不支持全部等级。
- 更高等级不保证结果正确，仍需测试和审查。

### 操作步骤
1. 根据任务复杂度选择初始等级。
2. 用低风险样例比较延迟、用量与结果质量。
3. 记录模型、端点和实际用量。
4. 对关键结果执行独立验证。

### 命令或配置示例
```text
loushang --thinking medium -p "分析失败原因。"
loushang --thinking high -p "制定并验证迁移方案。"
```

### 验证方法
- 模型请求成功接受或明确降级该参数。
- 选择带来的延迟和成本处于可接受范围。

### 注意事项
- 不要把隐藏推理内容当作必须保存的审计材料。
- 敏感输入不应因提高思考强度而扩大暴露范围。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“思考强度与输出”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。
