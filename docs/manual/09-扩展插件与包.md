# 第8章 扩展、插件与软件包

> 文档版本：V1.0.0

说明项目级扩展、Manifest、贡献发现以及可复用资产的安装和更新。

本章以用户可执行操作为主，命令和路径均应在目标安装环境中再次核对。

## 8.1 扩展模型

Extension 是项目级 Python 代码，可以注册生命周期钩子、工具、动态资源、命令和附加参数。

### 功能要点
- 扩展通过推荐的 register(api) 协议贡献行为。
- 扩展代码与主进程处于同一信任边界，应按可执行代码审查。
- 贡献来源应在 /extensions、/tools 或 source-info 中可见。

### 操作步骤
1. 创建独立扩展目录或 Python 文件。
2. 实现 register(api) 并注册最小贡献。
3. 以 --extension 显式加载进行离线验证。
4. 检查诊断后再放入项目默认发现路径。

### 命令或配置示例
```text
loushang --extension ./extensions/example.py --list-commands
python examples/coding/extensions/01_lifecycle.py
```

### 验证方法
- 扩展加载成功且贡献数量符合预期。
- 关闭扩展后核心命令仍可正常运行。

### 注意事项
- 不要运行来源不明或未经审查的扩展。
- 扩展异常应被隔离并形成可读诊断。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“扩展模型”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 8.2 生命周期钩子

生命周期钩子允许扩展在会话和输入处理的特定阶段观察或改变行为。

### 功能要点
- 钩子顺序和失败处理影响最终会话语义。
- 输入钩子可以处理或转换输入，但应保留可追溯性。
- 钩子不应执行与用户目标无关的隐藏副作用。

### 操作步骤
1. 列出需要观察的生命周期阶段。
2. 为每个钩子定义输入、输出和失败策略。
3. 使用离线会话验证调用顺序。
4. 检查日志和诊断中是否存在重复或遗漏。

### 命令或配置示例
```text
python examples/coding/extensions/01_lifecycle.py
/reload
```

### 验证方法
- 钩子只在声明阶段触发一次或符合预期次数。
- 钩子失败不会破坏会话文件。

### 注意事项
- 不要依赖未公开的内部调用顺序。
- 钩子日志不得记录完整凭证或敏感提示。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“生命周期钩子”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 8.3 动态资源

扩展可以向会话贡献动态提示、上下文或其他资源，使项目知识在运行时参与工作。

### 功能要点
- 动态资源应具有稳定名称、来源和说明。
- 内容变更需要在 reload 后重新解析。
- 资源优先级和来源冲突应通过诊断可见。

### 操作步骤
1. 实现资源贡献函数。
2. 为资源设置唯一标识和最小内容。
3. 启动离线会话检查加载。
4. 修改资源后执行 /reload 并验证变化。

### 命令或配置示例
```text
python examples/coding/extensions/02_dynamic_resources.py
python examples/coding/extensions/12_online_dynamic_resources.py
```

### 验证方法
- 模型上下文包含预期资源且来源可识别。
- 重新加载后旧内容不会继续残留。

### 注意事项
- 动态资源同样计入上下文预算。
- 不要通过资源注入秘密或未经审查的指令。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“动态资源”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 8.4 自定义工具与命令

扩展可以注册异步工具和 slash command，为项目提供专用能力。

### 功能要点
- 工具应定义清晰参数、描述、返回值和错误语义。
- 扩展命令在 prompt 或 skill 展开之前按命令路由处理。
- 命令补全和列表应展示来源，避免名称冲突。

### 操作步骤
1. 实现小型、可预测且可测试的函数。
2. 注册工具或命令并提供说明。
3. 用 list-commands 和 /tools 检查发现结果。
4. 测试成功、失败和取消路径。

### 命令或配置示例
```text
python examples/coding/extensions/03_custom_tool.py
loushang --list-commands
/extensions
```

### 验证方法
- 自定义贡献显示正确来源和描述。
- 错误能够返回给会话而不导致进程崩溃。

### 注意事项
- 工具参数不得允许未经校验的任意路径或命令。
- 命令名称应避免覆盖核心行为。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“自定义工具与命令”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 8.5 扩展 Manifest

相邻的 loushang-extension.toml 可以声明扩展身份、权限等级、依赖和预期贡献。

### 功能要点
- Manifest 使加载前的静态检查和可见性更可靠。
- 实际注册贡献应与声明相符。
- 权限等级用于风险判断，不等于操作系统强制隔离。

### 操作步骤
1. 为扩展设置稳定 id、名称和版本。
2. 声明需要的权限、依赖和贡献。
3. 使用 /extensions <id> 检查详情。
4. 修改 Manifest 后 reload 并查看诊断。

### 命令或配置示例
```text
python examples/coding/extensions/05_manifest_visibility.py
/extensions <id>
```

### 验证方法
- Manifest 与加载的 Python 代码对应。
- 未满足依赖时产生明确诊断。

### 注意事项
- 不要仅凭 Manifest 信任扩展，仍需审查代码。
- 扩展升级时应同步更新版本和权限说明。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“扩展 Manifest”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 8.6 插件发现与开关

插件提供可复用的资源集合，可通过列表、来源和启停参数管理项目可用状态。

### 功能要点
- 插件来源和启用状态可以是项目级配置。
- 启用插件可能带来技能、扩展或其他资产。
- 禁用是配置状态变化，不一定删除已安装文件。

### 操作步骤
1. 运行 --list-plugins 检查现状。
2. 添加可信插件来源。
3. 启用目标插件并 reload。
4. 验证贡献后再加入团队默认配置。

### 命令或配置示例
```text
loushang --list-plugins
loushang --add-plugin-source <source>
loushang --enable-plugin <plugin>
loushang --disable-plugin <plugin>
```

### 验证方法
- 插件状态和来源可以使用 JSON 格式审计。
- 禁用后相关贡献不再进入新解析结果。

### 注意事项
- 添加外部来源前应验证发布者和完整性。
- 插件标识与包来源可能不同，不要混淆。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“插件发现与开关”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 8.7 软件包生命周期

Package 命令提供安装、卸载、物化、更新和更新检查等可复用资产管理能力。

### 功能要点
- package-scope 区分 global 和 project 安装范围。
- catalog 用于发现或解析包来源。
- 物化将包内容落到可检查位置，便于审计和定制。

### 操作步骤
1. 列出已知软件包和当前范围。
2. 从可信来源安装到 project 范围。
3. 检查文件和贡献后启用。
4. 更新前阅读变化并保留可回滚版本。

### 命令或配置示例
```text
loushang --list-packages
loushang --package-scope project --install-package <source>
loushang --check-package-updates
loushang --update-package <source>
```

### 验证方法
- 安装结果包含可追溯来源和版本。
- 更新后命令、技能和扩展仍通过验证。

### 注意事项
- 卸载和 remove-package 可能影响项目运行，应先检查依赖。
- 全局安装会影响多个项目，优先使用 project 范围。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“软件包生命周期”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 8.8 重新加载与诊断

/reload 重新发现 keybindings、extensions、skills、prompts 和 themes，适合开发和配置变更后使用。

### 功能要点
- reload 应建立新的解析快照，避免部分新旧状态混合。
- 扩展加载错误应出现在 /extensions 或诊断列表。
- 活跃工具和命令应在 reload 后重新核对。

### 操作步骤
1. 保存扩展或资源文件。
2. 执行 /reload。
3. 查看 /extensions、/tools 和命令列表。
4. 运行一个最小贡献测试。

### 命令或配置示例
```text
/reload
/extensions
/tools
```

### 验证方法
- 新资源出现，删除的资源不再可用。
- 错误贡献被诊断而不是静默忽略。

### 注意事项
- reload 不会替代进程级依赖升级。
- 正在执行的工具调用不应在中途强制重载。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“重新加载与诊断”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。
