# 第11章 诊断、导出与可追踪交付

> 文档版本：V1.0.0

说明调试记录、诊断包、会话导出、工作证据和交付检查。

本章以用户可执行操作为主，命令和路径均应在目标安装环境中再次核对。

## 11.1 诊断列表

诊断列表集中展示会话或运行时发现的问题，可用 TSV 或 JSON 形式查询。

### 功能要点
- 诊断应包含级别、来源、消息和可采取行动。
- diagnostics-limit 控制列表规模。
- 有诊断不一定表示任务失败，需要结合级别和上下文判断。

### 操作步骤
1. 运行默认诊断列表。
2. 切换 JSON 格式保存快照。
3. 按来源和级别分类。
4. 修复后重新运行并比较差异。

### 命令或配置示例
```text
loushang --list-diagnostics
loushang --list-diagnostics --list-diagnostics-format json
loushang --diagnostics-limit 100 --list-diagnostics
```

### 验证方法
- 每条诊断具有稳定来源和可读说明。
- 修复后的重复诊断消失或状态更新。

### 注意事项
- 不要只删除诊断记录而不解决根因。
- 共享诊断前应审查本地路径和敏感元数据。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“诊断列表”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 11.2 诊断包导出

diag-export 将诊断信息写入指定输出，便于离线分析和问题报告。

### 功能要点
- 诊断导出不需要启动普通模型会话。
- diag-output 应指向明确文件路径。
- 导出包可能包含配置来源、路径和错误上下文。

### 操作步骤
1. 选择项目内临时或受控输出位置。
2. 运行 diag-export。
3. 打开文件确认格式与完整性。
4. 清理秘密和个人信息后再共享。

### 命令或配置示例
```text
loushang --diag-export --diag-output diagnostics.json
loushang --source-info --source-info-format json
```

### 验证方法
- 输出文件存在且可以解析。
- 诊断内容覆盖问题发生的相关组件。

### 注意事项
- 不要把未经审查的诊断包提交到公开仓库。
- 问题解决后按保留策略删除临时导出。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“诊断包导出”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 11.3 Debug 与 Trace

debug 和 trace 参数用于记录更详细的运行过程，文件参数可把信息写入独立日志。

### 功能要点
- Debug 适合组件级问题，Trace 适合事件顺序和边界分析。
- 日志量和敏感度通常高于普通诊断。
- 应只为必要组件启用，并限制保留时间。

### 操作步骤
1. 确定需要观察的组件或主题。
2. 设置 debug-file 或 trace-file。
3. 复现一次最小问题。
4. 关闭详细记录并分析时间线。

### 命令或配置示例
```text
loushang --debug session --debug-file debug.log --list-sessions
loushang --trace tools --trace-file trace.log -p "复现问题"
```

### 验证方法
- 日志包含问题发生前后的关键事件。
- 关闭调试后正常运行性能恢复。

### 注意事项
- 日志可能包含提示、路径和工具参数。
- 长期启用 trace 会增加磁盘和性能开销。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“Debug 与 Trace”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 11.4 HTML 会话导出

HTML 导出提供适合人类阅读的转录、工具事件和相关会话信息。

### 功能要点
- 默认 export 可生成 HTML 或由扩展名推断格式。
- 导出页面应保持离线可打开。
- 样式不能掩盖错误、取消或未完成状态。

### 操作步骤
1. 选择明确的 .html 输出路径。
2. 执行导出并在浏览器打开。
3. 搜索关键用户消息和工具事件。
4. 审查敏感信息后归档或共享。

### 命令或配置示例
```text
loushang --export session.html
loushang --export session.html --export-result-format json
```

### 验证方法
- 导出文件包含完整目标会话。
- 关键事件顺序与原会话一致。

### 注意事项
- HTML 中的源代码和路径仍属于敏感内容。
- 不要使用公共图床或外部脚本承载私有会话资源。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“HTML 会话导出”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 11.5 JSONL 会话导出

JSONL 导出适合机器处理、迁移和后续导入，每一行应是独立 JSON 记录。

### 功能要点
- 事件顺序由文件行顺序表达。
- 解析器应容忍已知版本字段并拒绝损坏行。
- 导入前需要确认来源、完整性和兼容性。

### 操作步骤
1. 指定 export-format jsonl。
2. 逐行运行 JSON 解析检查。
3. 记录文件哈希或存储版本。
4. 在隔离环境试验导入。

### 命令或配置示例
```text
loushang --export session.jsonl --export-format jsonl
/import session.jsonl
```

### 验证方法
- 文件每一非空行都是合法 JSON。
- 导入后的消息和事件数量符合预期。

### 注意事项
- 不要执行导入文件中暗示的外部动作。
- 跨版本迁移前应保留原始副本。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“JSONL 会话导出”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 11.6 可追踪交付

可追踪交付要求把用户目标、实际修改、验证证据和未决风险连接起来。

### 功能要点
- 交付说明应先给出结果，再列出重要文件和验证。
- 测试通过只能证明覆盖范围内行为，不能代表全部正确。
- 未运行的检查和环境限制必须明确说明。

### 操作步骤
1. 回顾原始目标和验收条件。
2. 列出实际变更文件与行为变化。
3. 记录验证命令、状态和关键输出。
4. 列出遗留风险、人工步骤和回滚方式。

### 命令或配置示例
```text
git diff --stat
git diff --check
python -m pytest <relevant-tests>
```

### 验证方法
- 每项完成声明都有可检查证据。
- 交付者没有把计划或推断当成执行结果。

### 注意事项
- 不要隐瞒失败测试或范围外问题。
- 外部发布、合并和发送动作应单独报告。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“可追踪交付”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。

## 11.7 交付前检查清单

结束会话前应进行范围、质量、安全、版本和归档五类检查。

### 功能要点
- 范围检查确保没有修改无关文件。
- 质量检查覆盖格式、静态分析、测试和真实运行。
- 安全检查覆盖秘密、权限、依赖和外部副作用。

### 操作步骤
1. 查看工作树和差异。
2. 运行与风险相称的验证。
3. 检查会话、日志和导出中的敏感信息。
4. 生成最终摘要并保存必要证据。

### 命令或配置示例
```text
git status --short
git diff --check
loushang --list-diagnostics
loushang --export delivery-session.html
```

### 验证方法
- 工作树状态和最终摘要一致。
- 登记版本、文档版本和软件显示版本已核对。

### 注意事项
- 不要因时间不足跳过高风险变更的最小回归测试。
- 归档前确认导出文件访问权限。

### 记录建议
- 建议在会话名称、工作日志或交付说明中记录“交付前检查清单”的实际选择。
- 如实际结果与预期不同，应保留命令、状态码和最小复现信息。
