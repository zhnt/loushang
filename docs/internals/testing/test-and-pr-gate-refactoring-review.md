## 3. 视角二：执行性能与证据可信度

检查目标：减少的是重复工作还是覆盖；分片、共享构建、结果复用和时间报告是否可核验。

| ID | 原方案问题与证据 | 影响及优先级 | R1 修订与复核 |
| --- | --- | --- | --- |
| PERF-01 | “用例只执行一次”缺少身份边界；真实安装与源码运行、不同平台不能互相代替 | P1；可能错误去重必需场景，或拼接旧报告造成误绿 | §7 定义 tree/计划/node ID/平台/实际配置身份；报告保留 run/attempt 和结果，缺失不能填成功 |
| PERF-02 | 原提议强调按耗时分片，但缺少全集、交集、新用例、数据版本约束；现有插件按 node ID 哈希 | P1；性能改动可能导致重复或漏测；理论平衡不等于实测达标 | §7 明确确定性兜底、清单绑定版本、并集相等与交集为空；分片数量以总成本实测决定 |
| PERF-03 | 复用产物未明确可变状态与隔离；Windows 当前完整性读取属于实际授权/物料校验链路 | P1；错误缓存可能掩盖改变，安装测试可能被源码遮蔽 | §7 产物绑定 tree/锁/工具链/平台/参数，不共享 Product state/租约，保持失效与锁语义，安装在干净环境执行 |
| PERF-05 | “提交时证据加速合并”容易把本地结果或旧 PR head 检查当成当前合并候选证明 | P1；可能绕过必需检查或主分支推进后的验证 | §7 区分合并前候选验证与合并后复用；本地结果不替代远端必需检查；设计边界明确，实现扩展需单独验证 |
| PERF-04 | ≤10/15 分钟容易通过扣除排队或单次成功证明；已有 84 runner 分钟与墙钟是不同指标 | P2；性能结论失真 | §1/§9 保留原始总时间，区分排队和阶段，多次实际运行建基线，异常样本留存；目标仍待验证 |

场景复核：

1. 同次 Linux 源码用例同时属于能力报告与历史追溯：一次执行，派生报告保留同一来源。
2. 同 node ID 的 Windows 原生与 Linux 模拟配置：不去重成同一证据。
3. 分片历史里没有新用例：确定性分配，集合校验必须发现遗漏。
4. 构建缓存来源 tree 或依赖锁不同：不能命中相同产物身份。
5. main 的 tree 相同但分类策略版本或必需集合改变：执行计划失配，正常回退。

追加 R2 复核：46 分钟用例累计成本不能被分片数量隐藏；4/8 片估算仅说明直接减少分片的下界，不作为达标证据。新分片数量在分类、去重后实测决定。

不根据分片理论负载预测实际 runner 排队或故障率；恢复预算必须通过真实平台验证。

## 4. 视角三：维护、迁移与操作

检查目标：删除历史门禁时是否保持稳定入口、明确 owner、原子切换和可回退；暂停状态与恢复条件是否清晰。

| ID | 原方案问题与证据 | 影响及优先级 | R1 修订与复核 |
| --- | --- | --- | --- |
| OPS-01 | “删除 G16/G17 等 job”未明确其必要断言与报告消费者的迁移 | P1；旧工作流虽删除，能力或证据消费可能断裂 | §5/§6 建旧断言到新 owner/类别/平台/触发/报告映射，未迁移必要断言显式登记；只删除证明完全重复的用例 |
| OPS-02 | 选择器、needs、聚合与验证器分开改动可能让合法跳过失败，或让缺失任务误绿 | P1；稳定入口和失败语义受损 | §8 原子更新映射与机制，保留一个必需 quality-gate；影子选择或手动受控验证不形成第二条全量阻塞路径 |
| OPS-03 | “重组后恢复”可能整组恢复原矩阵；回退也可能重新启用暂停项 | P1；原有 20–34 分钟场景回到 PR 路径 | §6/§8 区分重组与恢复，暂停清单独立保留，逐个短场景验收；回退不自动恢复六类长工作流 |
| OPS-05 | root 只看到 reusable workflow 总结果，直接删除 selected-checks 可能看不到所选子 job/矩阵被跳过或缺失 | P1；合并汇总可能造成误绿 | R3 §8 及全量清单要求迁移完整观察与失败语义；替代证据不足时保留必要校验，不凭任务数量删汇总 |
| OPS-04 | 静态方案与实施验收没有清楚划界 | P2；文档绿或方案评审可能被当成实现完成 | 元信息、§8/§9/§10 声明 goal 暂停；阶段交付与具体证据明确，实现及恢复仍待执行 |

场景复核：

1. 删除 `g17-darwin-native`：先迁移终端模式、物理退出等独有断言，更新报告消费与 job 聚合，再删除历史 job。
2. 某能力的必要原生场景恢复：只启用该场景，不解除整个 AppService/Windows Shell 暂停组。
3. 共享构建失败：明确失败或受控回退，不将依赖它的测试归为“不适用”。
4. 回退新的报告机制：暂停清单仍保留；不重新触发旧的完整 native/crash/GC 组合。
5. 分类未完成但需要合并：不得省略必要用例放行；补归属或执行受控保守验证，暂停项不自动恢复。

### R3 全量范围复核

- 覆盖视角：全量清单包含 16 个工作流和全部 71 个源 job；逐用例/平台/配置的唯一断言仍须实施时核对，不把 job 层覆盖当成完整测试覆盖。
- 性能视角：顶层调用不等于额外测试，矩阵实例不等于源 job 数；相同文件不等于相同运行配置。合并按真实重叠与准备成本决定。
- 维护视角：所有阶段 job、模块回归、静态检查、核心/平台/专项、扩展、子汇总与最终必需入口都纳入审查；新增 OPS-05 约束避免子汇总删除后的观察盲点。

### R4 单元测试语义去重复核

- 覆盖视角：旧方案若要求历史 node ID 并集完全不变，会阻止用户要求的冗余用例删除。R4 改为必要行为/断言/输入分区覆盖保持，旧用例到保留集合映射可核对；独有边界、失败、权限和生命周期不删除。
- 性能视角：参数化只是减少代码，不能冒充减少执行；共享准备必须保留可变状态与 patch 隔离，避免为了少启动而串成长测试。
- 维护视角：共享逻辑的完整行为测试归所属模块，消费者使用合同保留；删除有 owner、替代证据及回退依据，数量减少不能单独作为完成证明。
