## 可直接交给执行 agent 的 Goal 描述

在楼上现有 Coding SDK、Method、HarnessWork、Harness/Session/Agent 与证据能力上，
实现一个真实、可查询、可中断并可核验完成的 Goal 最小业务闭环。选择一个具有
明确缺陷的小型项目，以“修复指定问题，使约定的测试通过，并遵守原始约束”为
具体目标。系统应保存目标身份、要求及其版本，按显式选定的 Method 组织下一批
工作，通过现有 Coding 执行路径实际修改代码，复用现有验证与证据消费能力检查
结果，再根据要求和证据决定继续修复、等待用户、暂停或完成目标。

这个目标可以跨多批 Work 推进。一次 Work 成功、模型声称完成、材料可读或某次
旧测试通过，都不能单独作为 Goal 完成依据。完成判断必须能追溯到当前要求、
实际被验证的代码与测试版本、验证命令和对应证据；验证不通过或证据不足时保持
未完成，并明确下一步和原因。不能通过删除、跳过或放宽约定测试来冒充问题修复。

本 Goal 的首个交付采用本地 SDK 入口、显式 Method 和调用方显式推进。架构设计
必须同时说明 Method 指导与模型规划如何共用要求、计划受理、Work 执行和目标
验收合同，避免后续另造运行时；模型自主规划的实际接入作为后续独立增量，不
计入本 Goal 的完成判据。显式推进也必须支持读取上一批事实后选择下一批，不能
退化成执行一次固定命令便宣称实现 Goal。

先按照架构方法补齐系统环境、组件关系、状态及关键交互，经过三视角评审并关闭
阻断项，再交用户评审重要工作件。用户接受相应设计范围后，才按该范围实施。
复用现有执行、输入、授权、取消、用量与存储机制；只增加承载 Goal 语义所必需
的记录、判断和 Product 集成。交付应包含真实 SDK 场景、适当的合同与故障验证、
三视角复核及可重复查看的验收证据。

## 首个真实场景

1. 选定可重复还原的小项目，先运行约定测试，保存原始失败事实及测试/工作区版本依据。
2. 创建 Goal，明确要修复的问题、约束、验收命令和必需证据，显式选择 Method。
3. 受理当前批次；Coding Session 经已有模型和工具路径实际修改项目，形成原 Work 事实。
4. 执行验证，读取报告及实际输出，检查其与当前要求、受测代码和测试的对应关系。
5. 若仍失败，下一次显式推进依据失败证据组织后续工作；若需要用户决定或达到本轮
   授权/批次限制，则停止派发并说明原因，不能无界重试。
6. 满足全部约定要求后记录完成决定及其证据。关闭并重开本地会话后，可以查到目标、
   历次工作及该决定；重开本身不自动重执行工作。

正常路径须通过真实 SDK 和实际模型/工具执行验证；预设补丁、固定模型回复或假的
验证输出可用于合同与故障测试，不能替代真实业务场景的验收。首个项目、Method、
模型配置及执行边界须在实施前确定并记录，不能执行后再调整成功标准。

## 必须满足的验收条件

| ID | 完成判据 |
| --- | --- |
| GM-01 目标与关系 | 有稳定 Goal 身份、可追溯的要求版本，以及目标、Method、计划修订、原 operation 的关联；operation→run 解析仍由 HarnessWork 负责，不复制整份 Work/Transcript 日志 |
| GM-02 方法与受理 | 真正使用显式 Method 组织工作并保留其必要约束；受理前明确覆盖哪些要求、需要哪些证据、能核验哪些权限/资源边界。无法满足的约束明确等待或拒绝，不将提示文本当作已执行保证 |
| GM-03 多批推进 | 同一目标可关联多批原 Work；失败证据能影响后续工作选择，保留受理历史，不原地改写正在执行的 WorkRunSpec。无新证据或可行下一步时停止并给出理由 |
| GM-04 完成裁决 | 成功场景有原始失败→实际修复→最终验证的证据链；约定测试和约束确实满足。陈旧验证、缺失/损坏/不完整材料、仅 Work completed 或模型自报完成均不能使目标完成 |
| GM-05 用户控制 | 暂停后不再受理新批次，显式恢复需重新核对条件；放弃、执行取消和未知效果分别呈现。追加/修订/撤回要求必须记录变更并重新判断既有计划和证据的适用性，沿用原输入路径 |
| GM-06 重开与异常 | 会话重开后能读取目标和关联事实；中断、不完整历史、发布失败或效果未知时不盲重试、不自动重放、不虚报成功，明确哪些信息已知、哪些需要核对 |
| GM-07 复用与兼容 | 现有 steer、follow-up、text、image、普通 Coding 与 Method/Work 路径保持兼容；复用已有队列、Agent loop、Work、Blob、授权和用量事实，不建立第二套执行或原始 token 账本 |
| GM-08 真实交付 | 提供真实本地 SDK 修复场景及可重复核验的记录，完成与变更相称的离线检查和实现复核；固定回复测试与真实模型执行分别报告，不以测试数量或未跑完的回归冒充验收 |

首版需要支持“目标要求变化后的重新核对”，但不在本描述中冻结完整终态集合、
并发基数、journal 结构或批次控制 API。这些由前置架构设计比较并交用户评审。
证据与受测版本的绑定也须选定最小可行做法，优先使用现有版本信息及必要摘要，
不能直接扩张成通用工作区快照平台。

## 范围与实施前提

首个交付限于本地 SDK 和一个受控目标的纵向场景。多目标并行、跨会话迁移、远程
入口统一、离线后台调度、自动唤醒及模型自主规划不属于本 Goal 的完成范围；它们
与首版的关系须在架构中说明，不能默认为已经实现或在内部接受后自动扩大范围。

开发前需收束证据切片的集成与相关验证，明确可用源码基线；同时补齐环境图、
组件与已有系统关系、正常/失败/用户控制/重开交互，以及状态、计划准入、证据
适用性和推进交接等关键决定。三视角按职责与复用、运行与失败、数据与兼容组织，
保留固定修订及问题处置证据。重要架构工作件仍由用户评审，本描述生成不等于
架构接受或实施启动。
