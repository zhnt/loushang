## 需求表述

请以同步后的 main 为事实基线，遵循既定架构方法，对 Goal、Method 和 Work 的
职责、边界及协作方式进行系统设计。先明确使用者要达成的结果，再从系统环境、
功能、组件、接口和交互逐步展开，形成能够解释正常执行与关键失败场景的架构。
在环境关系、组件归属、关键机制和决策尚未梳理清楚之前，不开始 Goal 功能开发。

Goal 应兼容既有 Method 和 Work，支持两种推进方式：用户选择 Method，由方法
契约指导目标达成；或由大模型围绕目标自主规划任务。两种方式应复用共同的履约
和执行机制，也允许在方法约束内进行模型自主规划，避免建立两套执行系统。

设计应充分复用主线已有能力，区分已经具备的功能、必要的集成增量和独立增强。
旧实现仅作为架构分析素材，不继承其结构、格式、测试数量、工期或完成率结论。
不得为了交付 Goal，顺带重建输入队列、Agent loop、工具审批、原始用量账本或存储
系统；确有边界调整时，应说明驱动、替代方案、影响及兼容路径。

## 1. 需求、概念与系统环境

先建立需求和场景清单，明确范围、质量要求、适用环境与已有约束。至少说明：

- Goal 的目标、约束、验收条件及控制，与 Method 定义、计划、Work 履约和执行事实
  的区别；明确身份、关系、基数、状态、生命周期和事实归属。
- 方法指导、模型规划以及两者结合的用户场景；普通无 Goal 会话、既有 Method/Work
  使用路线如何继续工作。
- 用户通过 CLI、TUI、SDK 和 hosted 入口如何控制和观察目标；Product 在领域解释、
  方法选择、能力绑定和验收中的职责。
- 与已有 Session/Host/Agent、AI/model provider、工具/MCP、子代理、权限/审批/
  sandbox、workspace、Transcript/Blob、Work event log、展示和诊断的环境交互。

给出整体协作的系统环境图，以及必要的 Goal 边界视图。连接应标明调用/事件/数据
含义、方向和责任，避免把组件内部结构混成黑盒环境。按实际支持范围说明本地和
hosted 的运行载体、进程/存储位置、可信边界及失败责任；不预设额外分布式服务。

## 2. 功能发现、组件识别与已有组件关系

按照“候选功能→候选组件→功能映射→拆分/合并/保留→结构和接口”的顺序推导，
不从类名或目录数量反推架构。以下是待分析的职责，不预先规定每项必须独立成组件：

| 责任域 | 应明确的职责 | 与既有能力的关系 |
| --- | --- | --- |
| Goal | 目标与要求管理、控制、推进决策、预算策略、进展和最终验收 | 新目标语义；执行/记账事实优先复用原 owner |
| Method | 方法资源、选择、编译、裁剪、约束及验收投影 | 盘点现有 MethodRuntime/MethodPlan，保留方法定义权威 |
| 规划与绑定 | 模型提出计划、方法适配、run-specific 工作契约、计划校验 | 明确 Product、Goal 与 Work 的适配边界，不自造执行权 |
| Work / HarnessWork | 受理、计划和步骤执行、事件、产物引用、取消、终态及回放 | 复用 canonical HarnessWork；保留 loushang.work 兼容入口 |
| 执行与通用基础能力 | 会话、队列、模型/工具调用、权限、原用量、持久化、展示 | 原 Harness/Agent/AI 等组件继续拥有，不在 Goal 中复制 |

最终组件图须逐一注明职责、不负责什么、拥有的状态、输入输出、依赖和生命周期；
说明哪些直接复用、哪些小幅扩展、哪些确需新增，以及为什么。包、逻辑组件和运行
进程分别表达，不将其混为一谈。遵守 Harness 不反向依赖 Method/HarnessWork 等
既有边界；若确需改变，通过共同父级决策处理，不以适配器名称掩盖反向依赖。

## 3. 组件接口与关键交互

用场景和时序图追踪实际入口、责任移交和可观察结果，至少覆盖：

1. 创建 Goal→选择 Method→绑定 Work→执行→结果/产物→Goal 验收。
2. 创建 Goal→模型规划→计划受理→Work 执行→证据反馈→继续或重新规划。
3. 运行中追加要求、steer/follow-up、改目标/计划，以及最终完成期间的新输入。
4. pause/resume、interrupt、cancel、close，含原 Work 已终态、在途动作和子执行。
5. 正常停止、失败、未知结果、重开/恢复，以及预算到限或用量尚不完整。
6. Goal、Work、Method 不同层面的完成/验收之间如何关联，避免自动等同。

关键接口要说明调用者、权限、先决条件、结果、失败、幂等/重复调用、取消及寿命。
场景需要哪一个排序点或收尾保证，应明确由哪个现有 owner 提供、是否需要增量；
不能用“原组件负责”或“增加一次检查”代替机制，也不为假想问题堆叠通用协议。

## 4. 必须作出的关键决策

围绕以下问题比较可行方案，记录选择、理由、代价、兼容影响和重新评估条件：

- Goal 与 Work 是什么关系，一目标如何关联多次履约、多个计划和后代执行；谁保存
  哪类状态，谁唯一决定该层终态，如何避免重复生命周期与双重日志。
- Method 的必须条件与模型自主空间如何划分；如何选择或切换方式，是否允许混合。
- 计划如何冻结、修改、偏离和重新规划；当前 Work 尚未提供的动态能力如何处理。
- 推进和最终验收由谁组织；Work completed、模型完成建议与 Goal complete 如何区别。
- 用户输入、控制操作、最终完成和在途执行如何排序，暂停/中断/恢复如何保持一致。
- 规划、执行、验收、重试、压缩和子执行如何归属原用量并受统一预算策略约束。
- 当前身份、Goal 控制权限和历史数据如何分离，同时复用既有工具审批/sandbox。
- 可选装配、唯一实例、刷新和退出边界；持久状态、恢复、导出及升级回退的支持范围。
- Goal 的最小必要增量是什么；哪些输入/持久化增强应独立交付，如何控制复杂度。

“原文图片先落盘再处理、User 确认后关联、覆盖空闲和运行中追加”仍保留为明确需求。
其范围、受理/排队/处理的含义和存储边界要单独说明，不默认为所有 Goal 启用的
强制前置，也不因单列而删除。已有 text/image/steer/follow-up 不重新列作缺失功能。

## 5. 架构产物、评审与开发前置条件

产物可组织为少量互相引用的文档，至少包含：

- 主线能力/复用盘点，标明基线及源码事实；Current、候选设计、已接受 Target 分开。
- 需求与关键场景、系统环境图、组件结构及职责/功能映射。
- 接口合同、组件交互时序、重要状态/领域数据及存储权威关系。
- 关键 ARD，包含备选方案、取舍、风险、必要验证和实际接受范围。
- 需求→组件→交互/决策→验证的追溯，及独立三视角评审和意见处置记录。

三视角至少覆盖：职责/复用/复杂度；运行/并发/失败；数据/权限/兼容/交付，并检查
相关决定组合后是否一致。基于固定修订评审，阻断问题必须处理并复核；未验证的
假设显式保留，不能据局部通过宣称整个设计或功能完成。

开发前应能从文档清楚回答：有哪些组件、为什么需要、怎样协作、复用了什么、
改动什么、关键失败由谁负责、怎样验证。架构接受不等于实现完成，也不自动撤销
用户暂停开发的指示；设计包完成后先汇报，待用户明确恢复功能开发。
