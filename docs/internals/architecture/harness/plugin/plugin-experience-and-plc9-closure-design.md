- [Capability Graph projection](../capability-dependency-and-mount-lifecycle.md#diagnostics-and-observation);

At the start of this candidate, three user journeys required work; the status
section above records which parts now have local evidence:

1. A user can list installed Plugins, but cannot yet obtain one complete,

2. An ordinary author can compile a data Skill package, but manually writes

## Decision: One Pipeline, Three Distinct Experiences

```text
native Resource -> native source discovery -------------------------+
                                                                  |
author source files -> explicit offline build -> plugin.json + IR  |
  -> inert validation -> Package/Product admission and selection --+
  -> owner-bound Resource / Tool / Capability generations
  -> Session capture + Model Input evidence
  -> read-only explanation; separately authorized retirement/repair
```

The three experiences share identities and evidence, not authority:

| Experience | Owner and permitted work | Explicit limit |
| --- | --- | --- |
| Authoring | The public `loushang.plugin` SDK compiles immutable intent into canonical files; optional author-invoked tooling writes files and reports diagnostics. | No install, Approval, Package Store, registry, Graph, Session, or live binding authority. |
| Management | Product adapters call the existing management application and Package Product operations; read models join owner facts. | A1 desired-state operations do not impersonate A2 acquisition/publication or domain cleanup. |
| Runtime | Product composes; Package, Resource, Tool, Capability, Approval, Sandbox, and Process owners admit, publish, execute, and retire their exact state. | No ambient Plugin context, second effective clock, universal hot reload, or cross-owner transaction. |

The Product Kernel, Agent loop, authorization, Approval coordination, Sandbox,
Graph Binder, and owner cleanup remain outside ordinary Plugin replacement.
Native Resources need no Plugin Instance merely to be discovered.

### Management binding boundary

Harness owns the management application ports, query-only command guard,
empty-owner read projection, configured Source inspection and read-model
assembly. A Product supplies a small profile containing Product identity,
installation scope, scope identity, workspace root, revision namespace and
current Source strings. This is a typed, immutable fact snapshot. Product
behavior that cannot be represented as facts enters through narrow owner ports
(for example, settings validation, Product selection, and compatibility
migration), rather than a callback bag or string-keyed strategy configuration.
The Product adapter still owns settings validation, private state layout,
legacy compatibility migration, Package Product selection, startup leases and
stable Product error codes. A query binding must not expose command submission
even if its underlying owner has a write method; opening it must not create
state or repair a partial journal. This split is now implemented for the
Coding CLI read binding and Source projection. A generic profile cannot decide
which Product consumer will use a declared Resource.

## Read-Only Composition Preview And Explanation

### Two distinct questions

`inspect` answers **what the package declares**. It is inert and may read a
bounded local candidate before install, but identifies the captured bytes and
digest rather than trusting a mutable path or version label. It grants no
admission authority; installation revalidates the exact artifact against the
then-current Product scope and policy. The first `preview_current` answers
**what an already installed, selected data-only composition would contribute
to a new Session for a specified Product and scope**. It uses current Product
policy and captured owner facts; it never evaluates a Python Definition,
consumes an Approval, creates a Worker, acquires a live owner generation,
repairs a journal, or changes desired state. An executable contribution whose
final plan requires authorized preflight is labeled
`requires_authorized_preflight`.

A later candidate-overlay preview requires a transport-neutral intent with an
operation (`install`, `update`, or `enable`), installation key, captured
artifact digest, predecessor revision, and proposed desired state. It must
model replacement of the same Plugin identity, disabled updates, and two
packages contributing the same Resource name. Until that intent and its
stale/conflict semantics are accepted, the Product cannot claim a proposed
local package would be selected.

`explain` answers **what was actually selected, captured, and retired**. It
joins the current `PluginManagementReadModelProjector`, Product selection
trace, Package Product result, Resource Catalog decision, Capability Graph
Projector, and Session capture by exact identities. None of these projections
may become a second writer or infer another owner's missing fact as success.

### Evidence and consistency contract

Each answer identifies Product, scope, request, snapshot time, relevant owner
revisions, candidate Plugin/revision, selected contribution identities, exact
owner decision, and a finite status such as `selected`, `rejected`, `blocked`,
`unknown`, `draining`, or `restart_required`. It includes the responsible owner
and a stable diagnostic code. Raw credentials, private paths, arbitrary
configuration, Resource bodies, and model prompt text are excluded by default.
An authorized Session view can refer to persisted Model Input evidence; a
preflight view cannot claim that a declaration reached a model.

An assembled read is not a cross-owner atomic snapshot. It reports observed
per-owner facts and revisions, with provenance and any skew or missing owner
evidence. An optional bounded recheck can detect revision drift observed
during assembly, but equal revision vectors cannot prove cross-owner causal
consistency; content-addressed owners may also return to the same revision.
The result therefore never claims a globally `consistent` snapshot unless a
separately accepted owner capture contract supplies that guarantee. Drift or
missing evidence produces typed `stale_snapshot` or `partial_evidence` fields.
No query retries with writes, repairs pending tails, or presents a missing
owner fact as `active`. A Package A2 failure before management handoff remains
an A2/Package fact linked by exact operation identity; it is not inserted into
an A1 journal.

Read-only behavior covers adapter construction, binding acquisition, normal
queries, and failure paths. Query bindings must open existing evidence without
ledger tail repair, Product activation, or an A2 recovery call. Absent
workspaces, incomplete tails, and unadmitted epochs return explicit unknown or
error states without changing files or executing Plugin code. If an existing
owner has no truly inert reader, this view waits for one rather than using its
activating runtime constructor.

composition; proposed-selection impact remains behind the candidate-overlay
gate above. Explain separately shows existing Session pins, pending Resource refresh,
and `restart_required` where the owner cannot refresh a sealed Provider or
dependency. A graceful disable affects future composition; emergency revoke
uses the existing stronger authority path. A read-only query can suggest the
next operator action but cannot take that action.
